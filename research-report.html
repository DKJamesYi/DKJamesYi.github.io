초록 (Abstract)

본 연구는 생성형 AI 기반 코드 작성 패러다임인 '바이브 코딩(Vibe Coding)'의 확산이 기업 내 비전공자(Non-Major / Citizen Developer)의 개발 참여 양상을 어떻게 변화시키고 있는지를 분석하고, 이를 안정적·지속적으로 뒷받침하기 위해 기업이 갖추어야 할 제도적·조직적·기술적 지원 환경의 구성 요소를 도출하는 것을 목적으로 한다.

연구 방법으로는 (1) 공개 자료 및 도구 공식 문서를 검토한 문헌 검토, (2) 연구팀이 실제로 구축·운영 중인 국내 대기업 사내 AI 개발 파이프라인에 대한 사례 분석, (3) 운영자·사용자로 참여하며 수집한 참여 관찰 자료를 병행하였다.

분석 결과 비전공자 개발 참여를 안정화시키기 위해서는 ① 공용 AI 코딩 계정·도구 제공, ② 표준화된 배포 인프라(셀프서비스 PaaS), ③ 사내 가이드·교육 체계, ④ 보안·거버넌스 정책, ⑤ 운영자–사용자 협업 채널의 다섯 가지 축이 통합적으로 마련되어야 함을 확인하였다. 본 연구는 이를 토대로 5층 구조의 "비전공자 개발 참여 지원 프레임워크(NDD-SF: Non-Major Developer Support Framework)"를 제안하며, 연구팀이 직접 구축한 GitLab + Coolify 기반 파이프라인을 적용 사례로 제시한다.

주제어(Keywords): 바이브 코딩, 시민 개발자, 생성형 AI, 기업 디지털 전환, 셀프서비스 인프라, AI 거버넌스, 개발 민주화

1 서론

1.1 연구 배경 및 필요성

2022년 ChatGPT 공개 이후 LLM(Large Language Model)의 코드 생성 능력이 비약적으로 발전하면서, 2025년 초 Andrej Karpathy가 제안한 "바이브 코딩" 개념은 산업계 전반으로 빠르게 확산되었다. 과거에는 프로그래밍 언어 문법과 알고리즘에 대한 사전 지식이 개발 활동의 진입장벽이었다면, 오늘날에는 자연어로 의도를 전달하기만 해도 작동하는 코드를 얻을 수 있는 환경이 일반화되었다.

이러한 변화는 사내 디지털 전환(Digital Transformation, DX)의 양상을 근본적으로 바꾸어 놓았다. IT 부서에 의뢰하지 않고도 현업 부서의 비전공자가 직접 도구를 만들어 사용하는 사례가 폭증하고 있으나, 대부분의 기업 인프라·정책은 여전히 전문 개발자 중심으로 설계되어 있어 다음과 같은 갭이 발생한다.

A

인프라 갭

비전공자가 만든 산출물을 호스팅·배포·관리할 표준화된 절차 부재

B

거버넌스 갭

공용 AI 계정·민감 정보 처리·권한 관리에 대한 명확한 사내 규정 미비

C

역량 갭

'프롬프트는 가능하지만 배포·디버깅은 모르는' 중간 단계 사용자 지원 부재

1.2 연구 목적

  1. 바이브 코딩 확산이 기업 내 개발 참여 구조에 미친 변화를 정량·정성적으로 규명한다.
  2. 비전공자 개발 참여를 저해하는 제도적·기술적 장애 요인을 식별한다.
  3. 실제 도입 기업의 사례를 분석해 필수 지원 환경 요소를 추출한다.
  4. 이를 통합한 비전공자 개발 참여 지원 프레임워크(NDD-SF)를 제안한다.

1.3 연구 문제

RQ1. 바이브 코딩 도입 이후 비전공자의 개발 참여는 어떤 단계로 진화하는가?

RQ2. 비전공자가 개발 결과물을 운영 환경까지 가져가는 과정에서 가장 큰 마찰점은 무엇인가?

RQ3. 기업이 제공해야 할 제도적·기술적 지원 환경은 어떤 구성 요소로 이루어지는가?

RQ4. 해당 지원 환경의 도입은 조직의 디지털 전환 성과에 어떤 영향을 미치는가?

1.4 연구의 범위 및 한계

본 연구는 국내 대기업·중견기업 환경을 주요 대상으로 하며, 스타트업·공공기관은 사례 비교 차원에서만 다룬다. 시간적 범위는 LLM 기반 코딩 도구가 대중화된 2023년 1월부터 2026년 3월까지의 약 39개월로 한정한다. 또한 본 연구는 도구의 기술적 비교가 아닌 "제도적 환경"에 초점을 맞추므로, 특정 LLM 모델의 성능 평가는 다루지 않는다.

2 이론적 배경 및 선행 연구 검토

2.1 바이브 코딩의 정의와 특성

정의

바이브 코딩(Vibe Coding)이란 개발자가 코드의 라인 단위 구현보다는 의도와 맥락(vibe)을 자연어로 전달하고, 생성형 AI가 그에 부합하는 코드를 작성·수정·검증하는 방식의 협업적 코드 생산 패러다임을 의미한다. 이는 Karpathy(2025)가 제안한 개념으로, 기존의 페어 프로그래밍과 달리 인간의 인지 부하를 '구현'에서 '검수와 방향 설정'으로 이동시킨다는 점에서 구별된다.

2.2 시민 개발(Citizen Development)의 진화

시민 개발 개념은 본래 노코드/로우코드 플랫폼(Power Apps, Mendix 등)을 중심으로 논의되어 왔다. 그러나 바이브 코딩의 등장 이후 시민 개발의 범위는 단순한 폼·워크플로우 자동화에서 전통적 코딩 영역(웹 앱, 데이터 파이프라인, 마이크로서비스)까지 확장되고 있다.

구분 1세대 (~2018) 2세대 (2018~2022) 3세대 (2023~)
도구 매크로 / VBA 로우코드 플랫폼 LLM 기반 코딩 어시스턴트
산출물 스프레드시트 자동화 폼·워크플로우 앱 웹앱, API, 데이터 파이프라인
주 사용자 현업 파워유저 업무 분석가 전 직군의 비전공자
운영 방식 개인 PC 벤더 SaaS 사내 PaaS / 컨테이너

2.3 선행 연구 검토

시민 개발(Citizen Development)과 생성형 AI 코딩 도구의 효과성에 관한 산업·학계의 논의는 주로 도구 자체의 생산성 향상에 초점을 맞추어 왔다. 그러나 도구를 둘러싼 기업의 제도적 환경—인프라 표준, 보안 정책, 운영자–사용자 협업 모델—을 통합적으로 다룬 논의는 아직 충분히 이루어지지 않았다. 특히 한국 기업 맥락에서 사내 보안 정책, 망분리 환경, 거버넌스 모델을 함께 고찰한 연구는 매우 제한적이다.

ℹ️
본 연구는 정량적 시장 추정치를 인용하기보다, 실제 기업의 도입 사례와 실무자 인터뷰를 통해 제도적 환경의 구성 요소를 직접 도출하는 데 초점을 둔다.

2.4 분석 프레임워크

본 연구는 정보시스템 도입 분석에 널리 활용되는 TOE 프레임워크(Technology–Organization–Environment)를 바이브 코딩 맥락에 맞게 재구성하여 분석 도구로 사용한다.

T

Technology

AI 코딩 도구, 사내 PaaS, 코드 저장소, 배포 자동화 파이프라인

O

Organization

거버넌스 체계, 운영자–사용자 협업 모델, 교육·역량 개발 프로그램

E

Environment

보안·컴플라이언스 규제, 산업별 정책 환경, 외부 협력사 관계

3.3 분석 절차

수집한 자료는 TOE 프레임워크의 세 축(Technology / Organization / Environment)을 따라 정리한 후 구축 단계별로 발생한 의사결정과 마찰점을 횡단 비교하였다. 본 연구는 통계적 일반화보다 실제 환경에서 작동하는 지원 모델의 구성 요소를 도출하는 데 목적이 있으므로, 탐색적 사례 연구(Exploratory Case Study) 접근을 채택하였다.

ℹ️
연구의 성격: 본 연구는 KAIST 정보경영석사과정 졸업 프로젝트로서 연구팀이 실제로 구축·운영 중인 사내 환경을 1차 자료로 활용한 실무 기반 사례 연구이다. 외부 인용 통계나 인터뷰 데이터는 포함하지 않으며, 사내 자료의 일부는 익명화하여 보고한다.

4 사례 분석

4.1 사례 기업 개요

A사 (국내 대기업, 건설/엔지니어링)

연구팀이 소속되어 직접 구축·운영 중인 사내 AI 개발 파이프라인 사례. 디지털솔루션그룹 / AX 추진반이 GitLab + Coolify + Webhook 기반의 셀프서비스 PaaS를 자체 구축하고, 사내 사용자·운영자·외부 협력사용 가이드 체계를 운영 중이다. 본 보고서의 4.2~4.4절은 이 사례에 대한 구축·운영자의 1차 관찰 기록을 토대로 작성되었다.

4.2 도입 타임라인

2023 Q1

비공식 도구 사용 단계

현업 부서가 개인 ChatGPT 계정으로 코드 생성. IT 부서 미인지 상태로 사내 데이터 유출 우려 발생.

2023 Q4

금지 vs 활용 갈등 단계

보안팀의 외부 AI 서비스 차단 정책과 현업의 활용 요구가 충돌. 셰도우 IT 현상 심화.

2024 Q3

공용 계정·전용 환경 마련

디지털솔루션그룹이 부서 단위 공용 AI 코딩 계정을 발급, 사내 가이드 페이지 게시.

2025 Q2

셀프서비스 PaaS 도입

Coolify 기반 컨테이너 PaaS와 사내 GitLab을 연동. 현업이 직접 Push만 하면 자동 배포되는 환경 구축.

2026 Q1

거버넌스 정착 단계

전산작업의뢰–자동 세팅–Teams 안내로 이어지는 통합 워크플로우 정립. 외부 협력사용 별도 가이드 운영.

4.3 구축·운영 과정에서 관찰된 주요 마찰점

연구팀이 운영자·사용자 양쪽에서 파일럿을 진행하며 관찰한 비전공자의 주요 마찰점은 다음과 같다.

📝 "코드를 만들었는데, 어디에 올려야 하는지 모른다"

가장 처음 부딪히는 장애물은 호스팅 절차의 불투명성이었다. AI는 코드는 잘 짜주지만 배포 환경 차이까지 알려주지는 못한다.

🔐 "보안 규정 위반인지 아닌지 판단이 어렵다"

무엇을 AI에 입력해도 되고 무엇은 안 되는지에 대한 명확한 기준이 없을 때 자가 검열로 인해 활용 자체가 위축되는 양상이 관찰되었다.

🚧 "Docker, GitLab 같은 단어 자체가 장벽"

AI가 생성한 코드 자체보다 주변 인프라 용어와 흐름이 비전공자에게 더 큰 학습 부담으로 작용했다.

🤔 "에러가 나면 누구에게 물어봐야 하는지 모른다"

전통적 IT 헬프데스크는 "사용자 본인이 만든 코드"의 디버깅을 자신의 업무 범위로 인식하지 않는 경우가 많아 책임 사각지대가 발생하였다.

4.4 사례 시사점

구축·운영 과정에서 관찰된 마찰점과 그 해소 시점을 종합하면, 비전공자의 개발 참여를 정착시키기 위해 다음 다섯 가지 요소가 통합적으로 작동해야 함을 확인할 수 있다.

  • (1) 단일 진입점이 되는 가이드 페이지 — 사용자/운영자/외부 협력사로 트랙을 분리하여 제공
  • (2) 자동화된 배포 인프라 — Push 한 번으로 빌드·배포가 끝나는 셀프서비스 PaaS
  • (3) 운영자가 명확히 식별되는 협업 채널 — 전산작업의뢰 → Teams 안내로 이어지는 표준 흐름
  • (4) 공용 AI 계정과 사용 수칙 — 민감 정보 입력 금지·외부 공유 금지 등 명문화된 가이드라인
  • (5) 외부 협력사를 포함한 차등화된 절차 — SSL VPN·계정 발급을 별도 트랙으로 분리
💡
가이드 페이지를 별도 산출물로 우선 구축한 결과, 운영자에게 들어오는 1:1 반복 문의가 눈에 띄게 줄어드는 양상이 관찰되었다. 이는 단순히 정보 전달이 아니라 "무엇을 모르는지조차 모르는 상태"를 해소하는 메타 자원으로서 가이드가 기능했음을 시사한다.

5 비전공자 개발 참여 지원 프레임워크 (NDD-SF)

4장에서 도출한 다섯 가지 공통 요소를 기반으로, 본 연구는 비전공자 개발 참여 지원 프레임워크(Non-Major Developer Support Framework, 이하 NDD-SF)를 제안한다. 이 프레임워크는 5개의 층(Layer)으로 구성되며, 각 층이 상호 보완적으로 작동할 때 효과가 극대화된다.

5.1 5층 구조

Layer 1 · 도구 계층

공용 AI 코딩 계정 (예: Claude Code 팀 라이선스), IDE 확장, 권한 통제 도구

Layer 2 · 인프라 계층

셀프서비스 PaaS, 사내 Git 저장소, 컨테이너 빌드/배포 자동화 파이프라인

Layer 3 · 가이드 계층

단일 진입점 가이드 페이지(사내·외부 협력사 분리), 단계별 체크리스트, 트러블슈팅 자료

Layer 4 · 거버넌스 계층

데이터 입력 가능 범위 정책, 공용 계정 운용 수칙, 보안 검토 절차, 외부 협력사 차등 권한

Layer 5 · 협업 계층

전산작업의뢰 시스템, 자동 세팅 도구, Teams/Slack 협업 채널, 운영자–사용자 정기 회의체

5.2 적용 시나리오: "현업 비전공자 P씨의 1주일"

Day 1

아이디어 발굴 & AI 도구 사용

P씨는 공용 AI 코딩 계정(Layer 1)에 로그인하여 자연어로 데이터 시각화 웹앱을 작성한다.

Day 2

전산작업의뢰

가이드 페이지(Layer 3)의 안내에 따라 전산작업의뢰(Layer 5)를 등록한다.

Day 3

운영자 자동 세팅 & Teams 안내 수신

운영자는 자동 세팅 도구로 GitLab 저장소·Coolify 프로젝트를 5분 내 생성, Teams 메시지로 안내(Layer 5).

Day 4

코드 Push로 자동 배포

가이드대로 토큰 발급 → Push 한 번으로 셀프서비스 PaaS(Layer 2)가 자동 빌드·배포.

Day 5

피드백 반영 & 거버넌스 점검

운영자는 정기 점검에서 P씨 앱의 데이터 입력 범위가 사내 정책(Layer 4)을 준수하는지 검토.

5.3 도입 효과 모델 (정성적 예측)

NDD-SF의 5개 층이 모두 갖추어진 경우와 그렇지 않은 경우, 조직의 개발 참여 성과는 다음과 같이 차별화될 것으로 예측된다. 본 표의 수치는 정량 측정값이 아닌 정성적 비교 모델이며, 후속 연구에서 실제 도입 조직을 대상으로 한 검증이 필요하다.

지표 NDD-SF 전면 도입 부분 도입 (가이드만) 미도입
월 신규 배포 건수 높음 중간 낮음
셰도우 IT 발생 빈도 매우 낮음 중간 매우 높음
운영자 문의 부하 낮음 (정형화) 중간 높음 (반복적)
보안 사고 위험 낮음 (정책 명문화) 중간 높음 (자가 검열 의존)

6 결론 및 제언

6.1 연구 요약

본 연구는 바이브 코딩의 확산이 비전공자의 개발 참여를 양적으로 증가시키는 동시에, 기존 기업 인프라·정책 체계와 마찰을 일으키고 있음을 확인하였다. 연구팀이 직접 구축·운영 중인 사내 AI 개발 파이프라인 사례를 분석한 결과, 단순한 도구 도입이 아닌 5층 구조의 통합적 지원 환경(NDD-SF)이 마련될 때 비로소 지속 가능한 개발 민주화가 가능함을 도출하였다.

6.2 학문적 기여

  • 기존 시민 개발 연구가 다루지 않았던 바이브 코딩 시대의 인프라·거버넌스 차원을 통합적으로 분석.
  • TOE 프레임워크를 한국 기업 맥락에서 재구성하여 적용한 사례 제시.
  • 실무에 즉시 적용 가능한 5층 구조 NDD-SF 모델 제안.

6.3 실무적 제언

🏢 기업 차원

  • 가이드 페이지를 최우선 1차 산출물로 구축할 것
  • 외부 협력사용 별도 트랙(VPN·계정 발급)을 분리 운영할 것
  • 공용 AI 계정의 사용 수칙을 사내 규정에 명문화할 것

📜 정책 차원

  • 중소기업의 셀프서비스 PaaS 구축을 위한 정부 지원사업 신설
  • 업종별 AI 코딩 거버넌스 표준 가이드라인 제정
  • 비전공자 대상 인프라 활용 교육 프로그램 보급

6.4 연구의 한계 및 향후 과제

본 연구는 단일 기업 사례에 기반한 탐색적 사례 연구이므로 일반화에 한계가 있으며, 외부 인용 통계가 아닌 연구팀의 직접 관찰 자료를 1차 자료로 사용하였다. 또한 NDD-SF의 효과를 정량적으로 검증하기 위한 후속 연구가 필요하다. 향후 연구에서는 (1) 다수 기업으로의 적용·비교, (2) 산업별 NDD-SF 변형 모델, (3) 도입 비용–효과 분석 등을 다룰 필요가 있다.
